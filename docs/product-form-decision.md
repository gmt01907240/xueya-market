# 学涯集市 · 产品形态技术选型决策报告

> 决策范围：在**暂不开发任何支付相关功能模块**的前提下，确定学涯集市后续优先投入的产品形态（网页端 / 移动端 App）。
> 适用阶段：竞赛提交、内测验证与早期运营。
> 版本：v1.0 ｜ 决策状态：已定稿

---

## 一、结论先行

**优先开发「网页端（Mobile-First 响应式 Web / H5）」，移动端 App 暂不启动，转为「条件触发式」备选方案。**

核心判断：

1. 学涯集市现有全部能力（资源库、搜索筛选、试读、下单、上传、沟通、AI 客服、学习计划）**已经运行在 Web 端**，继续投入 Web 的边际成本最低。
2. 目标用户（高校学生）的核心获客路径是**链接 / 二维码 / 群分享 / 搜索引擎直达**，H5「点开即用、无需安装」的转化路径最短。
3. 在支付模块冻结的前提下，App 最不可替代的优势（原生支付、推送、离线）**当前无法兑现**，投入产出比显著低于 Web。
4. Web 迭代周期约为 App 的 **1/3–1/4**，更符合早期「快速验证、频繁调整」的阶段诉求。

> 一句话：**先用 Web 把「找资料—试读—成交」这条主链路跑通并验证留存，再用数据决定是否值得为 App 买单。**

---

## 二、决策前置基线（项目现状）

选型必须建立在真实现状上，以下是本项目当前事实：

| 项目 | 现状 |
| --- | --- |
| 后端 | Node.js（`node:sqlite`）+ 自建 HTTP 服务，单体部署 |
| 前端 | 原生 JS 单页应用（`public/js/views/*`），无框架依赖 |
| 页面能力 | 首页、资料市场、资料详情、上传、求购、消息、卖家中心、我的、学习计划、客服、管理后台等 |
| 响应式 | `index.html` 已声明 `viewport`；`app.css` 已内置 `1080 / 980 / 900 / 880 / 680 / 600px` 多档媒体查询 |
| 数据资产 | 3196 所院校 + 883 个本科专业资源库，服务端索引，响应约 10ms |
| 交付形态 | 浏览器访问 + 单文件离线演示页 `demo.html` |
| 支付 | 按本次要求**冻结，不开发** |

**结论：Web 不是「要不要做」的问题，而是「已经做了、如何继续做深」的问题。App 则需要从零重建一套客户端。**

## 三、候选方案定义

| 方案 | 说明 | 与现状的关系 |
| --- | --- | --- |
| **A. Web 响应式（H5）** | 在现有 Web App 上做移动优先适配与体验打磨，浏览器/微信内直接访问 | 高度复用，增量投入 |
| **B. 移动端 App** | 原生（iOS/Android）或跨端（React Native / Flutter / uni-app）重写客户端 | 需重写 UI 与交互层，新增发布与合规链路 |
| C. 小程序（补充项） | 微信小程序，依附微信生态 | 可作 Web 之后的低成本补充，不作为本轮主选 |

> 本文主对比 A 与 B；C 作为后续可选项在路线图中提及。

---

## 四、选型依据：多维权衡

评分说明：5 分最优，权重合计 100%。

| 维度 | 权重 | Web（A） | App（B） | 说明 |
| --- | --- | --- | --- | --- |
| 与现有代码复用度 | 20% | 5 | 1 | Web 复用 90%+；App 需重写视图层 |
| 用户获取与转化路径 | 20% | 5 | 2 | H5 扫码/链接直达；App 需下载安装 |
| 核心场景匹配度 | 15% | 5 | 3 | 浏览/搜索/试读/下载均为轻交互，Web 足够 |
| 开发与维护成本 | 15% | 5 | 2 | App 双端 + 审核 + 发版 |
| 迭代速度 | 15% | 5 | 2 | Web 改完即发布；App 走审核 |
| 留存/推送/离线能力 | 10% | 2 | 5 | App 唯一明显优势 |
| 合规与发布复杂度 | 5% | 4 | 2 | App 需应用商店、隐私合规、签名证书 |
| **加权总分** | 100% | **4.65** | **2.05** | — |

**关键结论：除「留存/推送/离线」一项外，Web 在其余所有维度均领先；而该唯一优势在「支付冻结」阶段无法转化为交易闭环价值。**

## 五、用户场景适配分析

| 用户场景 | 典型动作 | Web 适配 | App 适配 | 判断 |
| --- | --- | --- | --- | --- |
| 发现资料 | 群内链接、扫码、搜索进入 | 点开即用，无需安装 | 需先下载，流失高 | **Web 胜** |
| 检索筛选 | 院校/学科/老师三维筛选、关键词 | 已实现，响应快 | 需重做交互 | **Web 胜** |
| 试读预览 | 前 10%–20% 试读、水印 | 浏览器原生能力足够 | 无额外收益 | **Web 胜** |
| 下单成交 | 生成订单、查看状态 | 已具备（支付暂冻结） | 原生支付为优势，但当前冻结 | **平** |
| 下载资料 | 下载已购文件 | 浏览器下载成熟 | 文件管理略优 | Web 略优 |
| 上传售卖 | 选文件、填信息、试读生成 | 已实现 | 相册/文件选择略顺 | **平** |
| 买卖沟通 | 站内会话、场景化快捷回复 | 已实现 | 推送提醒更强 | App 略优 |
| AI 客服 | 7×24 免登录咨询 | 免登录即可用 | 需先装 App | **Web 胜** |
| 学习计划打卡 | 生成计划、逐项打卡 | 已实现 | 打卡提醒更优 | **平** |
| 消息触达/召回 | 站内消息、公告 | 依赖主动访问 | 推送召回强 | App 胜 |

**统计：10 个核心场景中，Web 明确占优 6 项、持平 3 项、App 仅 1 项占优（且依赖推送能力）。**

## 六、开发成本评估

### 6.1 直接成本结构

| 成本项 | Web（A） | App（B） |
| --- | --- | --- |
| UI/交互改造 | 在现有样式上做移动优先适配 | 全量重写视图层 |
| 端数量 | 1（浏览器） | 2（iOS + Android）或跨端一套 + 适配 |
| 后端接口 | 基本复用 | 需新增鉴权、版本、推送、埋点接口 |
| 测试 | 单端 + 主流浏览器 | 双端 + 多机型 + 系统版本矩阵 |
| 发布 | 部署即生效 | 应用商店审核、签名、证书、灰度 |
| 合规 | 常规隐私政策 | 应用商店隐私清单、权限声明、备案 |
| 运维 | 一套 | 客户端版本兼容 + 强制升级策略 |

### 6.2 隐性成本（最易被低估）

- **应用商店审核不确定性**：功能描述、类目、内容合规均可能被驳回，形成不可控等待。
- **版本碎片化**：老版本客户端需长期兼容，接口无法自由演进。
- **双端一致性**：同一功能需在 iOS/Android 各验证一遍，回归成本翻倍。
- **推送与证书体系**：APNs、厂商推送通道、证书轮换，均需额外运维。
- **支付相关前置**：即便本轮冻结，App 上架通常要求完整账号/隐私体系，反而被迫提前处理支付与实名链路。

### 6.3 成本结论

> App 的**一次性建设成本约为 Web 的 3–5 倍**，**长期维护成本约为 Web 的 2–3 倍**；在支付冻结阶段，这些投入无法换来对应的交易价值。

## 七、迭代周期对比

以「一个中等功能（如新增一个筛选维度 / 一个表单页）」为统一标尺：

| 环节 | Web（A） | App（B） | 相对倍数 |
| --- | --- | --- | --- |
| 需求→开发 | 1 个周期 | 双端各 1 个周期 | ≈ 2× |
| 联调 | 快（同源接口） | 双端联调 + 兼容 | ≈ 2–3× |
| 测试 | 单端回归 | 多机型矩阵 | ≈ 2–3× |
| 发布 | 部署即上线 | 提审 + 等待审核 | 不可控（数天级） |
| 回滚 | 秒级回滚 | 需发新版 + 再审核 | 不可控 |
| 灰度 | 服务端开关可控 | 依赖商店分阶段发布 | 弱 |

**结论：Web 的完整迭代周期约为 App 的 1/3–1/4；且 Web 具备秒级回滚与服务端灰度能力，App 不具备。**

对本项目尤其重要：早期需求高频变化，**Web 的「改完即生效」是最大结构性优势**。

## 八、风险与缓解

### 8.1 选择 Web 的风险

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 移动端体验不如原生 | 触控、滚动、键盘遮挡 | 移动优先改造：底部导航、44px 触控区、安全区适配 |
| 微信内分享/支付受限 | 传播与转化 | 分享卡片优化；支付模块上线时再评估小程序 |
| 留存与召回弱 | 复访低 | 站内消息、公告、邮件；后续引入 PWA / 小程序 |
| 无系统推送 | 提醒触达弱 | 关键节点站内信 + 低成本 Web Push 评估 |

### 8.2 若选择 App 的风险

- 成本与周期显著上升，早期方向调整代价高；
- 审核不可控，可能错失竞赛/内测关键节点；
- 支付冻结导致 App 的核心价值无法体现，易形成「高投入、低回报」。

## 九、决策与路线图

### 9.1 决策

> **本轮优先 Web 响应式（Mobile-First），App 不进入开发排期。**

### 9.2 分阶段路线（均不含支付模块）

| 阶段 | 目标 | 关键动作 | 验收口径 |
| --- | --- | --- | --- |
| 阶段 0：移动优先改造 | 让现有 Web 在手机上「好用」 | 底部导航、触控热区、安全区、字体与间距、首屏性能 | 移动端核心流程可顺畅完成 |
| 阶段 1：Web 功能完善 | 打磨主链路 | 搜索筛选、试读、上传、沟通、AI 客服、学习计划体验优化 | 主链路无阻断、无占位内容 |
| 阶段 2：留存与召回 | 提升复访 | 站内消息、公告、PWA 可行性评估 | 复访与消息触达可度量 |
| 阶段 3：形态再评估 | 数据驱动决策 | 依据下方阈值判断是否启动 App / 小程序 | 达到阈值再立项 |

### 9.3 启动 App / 小程序的触发阈值（建议）

满足**任意两项**再评估启动：

1. 移动端日活达到稳定规模，且移动端占比显著高于桌面端；
2. 次周留存达到可运营水平，且留存瓶颈被定位为「缺少推送/快捷入口」；
3. 支付模块正式上线，且原生支付/推送能带来可量化的转化提升；
4. 出现明确的「必须依赖客户端」的能力需求（如离线缓存、后台任务、硬件能力）。

> 未达阈值前，一律以 Web 迭代为主，避免过早背上双端维护成本。

## 十、度量指标（决策验证）

选择 Web 后，应以数据验证决策是否正确：

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| 移动端占比 | 移动访问 / 总访问 | 判断移动优先改造的优先级 |
| 移动端首屏时间 | 关键页面加载 | 验证性能改造效果 |
| 主链路转化率 | 访问 → 试读 → 下单 | 验证 Web 能否承载成交 |
| 次周/次月留存 | 复访比例 | 判断是否真的需要推送/App |
| 移动端报错率 | 前端异常 | 移动兼容性监控 |

## 十一、附：一句话执行指引

- **做**：持续投入 Web 移动优先改造与功能完善；
- **不做**：本轮不启动原生/跨端 App，不引入双端维护成本；
- **看**：用移动端占比、转化率、留存三项数据，决定阶段 3 是否启动 App / 小程序；
- **前提**：全程不开发支付相关功能模块。
