# 从测试环境到真实用户：内测与公测落地方案

适用项目：学涯集市 · 高校学习资料交易平台
当前基线：单进程 Node 服务 + SQLite（WAL）+ 本地文件上传；支付为 `mock`；非生产环境默认写入演示数据，生产默认关闭；322 项自动化测试通过；尚未公网部署。
目标：在保证资金、个人信息与内容合规的前提下，按「预发 → 内测 → 公测灰度 → 全量」推进真实用户使用。

> 本文是发布执行方案，不替代 [deployment.md](deployment.md) 的安装命令；两者配合使用。

---

## 0. 三条发布红线

1. **资金红线**：未完成真实商户接入与回调验签联调前，只能以「模拟支付」内测，页面必须显著标识；不得向真实用户收取真实资金。
2. **数据红线**：生产库、预发库、演示库物理隔离；生产环境禁止写入演示账号与演示订单；学生实名信息最小化采集。
3. **合规红线**：论文范文类目仅限方法参考，保留合规提示、举报入口与下架机制；上线前完成用户协议、隐私政策与 ICP 备案（境内公网）。

任何一条不满足，不进入下一阶段。

## 1. 阶段总览

| 阶段 | 目标 | 用户范围 | 支付 | 放行条件 |
| --- | --- | --- | --- | --- |
| G0 生产化改造 | 补齐上线阻断项 | 无 | mock | G0 清单全部关闭，回归测试通过 |
| G1 预发验证 | 在类生产环境跑通全链路 | 内部 5—10 人 | mock | 预发验收表通过，备份可恢复 |

| G4 全量 | 稳定运营 | 全部合规用户 | 真实支付 | 连续 7 天指标达标，复盘完成 |

## 2. 环境配置与数据隔离

### 2.1 三套环境

| 项 | 开发/演示 | 预发 staging | 生产 prod |
| --- | --- | --- | --- |
| 域名 | localhost | staging.example.com（Basic Auth 保护） | market.example.com（HTTPS） |
| `DATA_DIR` | 项目 `data/` | `/srv/xueya-staging/data` | `/srv/xueya/data` |
| 数据库 | `xueya.db` | 独立库，禁止连生产 | 独立库，每日快照 |
| 上传目录 | `data/uploads` | 独立目录 | 独立目录 + 只读挂载给应用 |
| 演示数据 | 自动写入 | 可写入脱敏样本 | **禁止写入** |
| 支付 | `PAYMENT_MODE=mock` | `mock`，独立密钥 | `live`，独立商户与回调地址 |
| 管理员 | 演示 admin | 独立 staging 管理员 | 独立实名管理员，IP 白名单 |
| 日志 | 控制台 | 文件 + 控制台 | JSON 行日志，集中采集 |
| 备份 | 不需要 | 每日 | 每日全量 + 每小时 WAL 快照 |

### 2.2 生产环境变量基线

| 变量 | 生产值 | 状态 | 说明 |
| --- | --- | --- | --- |
| `NODE_ENV` | `production` | 已有 | 关闭开发行为 |
| `PORT` | `3300` | 已有 | 仅监听 127.0.0.1，由 Nginx 暴露 |
| `DATA_DIR` | `/srv/xueya/data` | 已有 | 必须持久化卷 |
| `PAYMENT_MODE` | `live` | 已有 | 未配齐渠道时自动不可选 |
| `WECHAT_*` / `ALIPAY_*` / `BANK_*` | 商户值 | 已有 | 与预发完全隔离 |
| `SETTLEMENT_DELAY_HOURS` | `24` | 已有 | T+1 结算 |

| `FEATURE_*` | 见 3.2 | **需新增** | 功能开关与熔断 |
| `ADMIN_IP_ALLOWLIST` | 办公网/VPN 出口 | **需新增** | 后台访问限制 |
| `LOG_LEVEL` | `info` | **需新增** | 日志级别 |
| `REQUEST_ID_HEADER` | `X-Request-Id` | **需新增** | 全链路追踪 |

### 2.3 G0 上线阻断项（当前代码需补齐）

| 编号 | 风险 | 现状 | 必须完成的改造 |
| --- | --- | --- | --- |
| G0-1 | 生产写入演示账号（含公开弱密码 admin） | 启动无条件 `seed()`，并打印演示账号 | 增加 `SEED_DEMO=false` 分支；生产禁止 seed 与凭据打印；首次启动用一次性初始化命令创建管理员 |
| G0-2 | 限流可被伪造 `X-Forwarded-For` 绕过或误伤 | 直接取 XFF 第一段 | 仅在 `TRUST_PROXY=1` 且请求来自受信代理时取 XFF，否则用 socket 地址 |
| G0-3 | 故障无法按请求追踪 | 仅 `console.error` | 为每个请求生成 requestId，输出 method/path/status/耗时/userId；响应头回传 requestId |
| G0-4 | 重启丢失在途请求 | 无 SIGTERM 处理 | 收到 SIGTERM 后停止接收新连接，等待在途请求与结算任务，超时强制退出 |
| G0-5 | 内测用户范围不可控 | 注册完全开放 | 注册增加邀请码校验；支持批次、有效期、使用次数 |
| G0-6 | 故障无法快速熔断 | 无功能开关 | 增加服务端功能开关与 `/api/meta` 公开开关；前端按开关隐藏入口 |
| G0-7 | 上传文件仅校验扩展名 | 大小与后缀白名单 | 增加 MIME/魔数校验、图片二次编码、压缩包解压炸弹限制；接入 ClamAV 或云查杀 |
| G0-8 | 后台权限过大且无审计 | 单一 admin 角色 | 管理员分角色（审核/财务/客服）；后台操作写审计日志；限制后台来源 IP |
| G0-9 | 隐私与协议缺失 | 无协议页面 | 上线用户协议、隐私政策、未成年人提示、论文合规提示与举报入口 |
| G0-10 | 数据库单文件容量与写入上限 | SQLite 单写者 | 明确阈值：写 QPS 持续 > 50 或库 > 2GB 时迁移 PostgreSQL；公测前完成一次容量评估 |

### 2.4 数据隔离规则

- 生产 `DATA_DIR` 与预发、演示目录不得相同；部署脚本启动前校验路径，发现指向 `data/` 直接退出。
- 禁止把生产库直接复制到预发；如需样本，先做脱敏（去除手机号、邮箱、实名材料、支付单号）。
- `secret.key` 每套环境独立；更换密钥会使全部登录态失效，必须走维护窗口。
- 上传文件按环境独立存储，生产下载只走鉴权接口，Nginx 不对 `uploads/` 提供直链。
- 备份文件加密存放，访问权限仅限运维；恢复演练在预发进行，禁止在生产试恢复。

### 2.5 权限管控

| 角色 | 权限 | 约束 |
| --- | --- | --- |
| 游客 | 浏览、搜索、查看公开资料、AI 客服 | 不可上传、下载、支付 |
| 注册用户 | 上传、购买、下载、评价、举报、学习规划 | 需登录；上传先机审再人审 |
| 卖家 | 上述权限 + 卖家中心、收益与结算 | 需完成身份/高校认证 |
| 审核员 | 资料审核、举报处理 | 不可改价、不可退款 |
| 财务 | 对账、退款审批、结算查看 | 不可审核内容 |
| 超级管理员 | 用户与权限管理 | 必须 IP 白名单 + 强密码，操作全审计 |

原则：一人一账号、后台不共享账号、权限按需授予、离岗即回收；每季度复核一次管理员名单。

### 2.6 发布流程（预发 → 生产）

1. 代码冻结：打 tag，确认工作区干净，322 项测试全绿。
2. 备份：生产 `data/` 全量备份并校验可解压；记录当前版本号。
3. 预发部署：使用与生产相同的 Node 版本、环境变量结构、反向代理配置。
4. 预发回归：执行第 5 节预发验收表 + 支付回调联调（mock 与沙箱）。
5. 生产发布：低峰期切换；先启动新进程通过健康检查，再切换 Nginx upstream。
6. 发布后 30 分钟观察：5xx、支付成功率、结算任务、登录成功率。
7. 记录发布日志：版本、变更、影响面、验证人、回滚点。

## 3. 内测方案

### 3.1 准入机制

- **邀请制**：注册必须填写邀请码；邀请码按批次生成，设置有效期与使用上限。
- **身份门槛**：至少完成手机号或高校邮箱其一验证；卖家必须完成实名/高校认证后才能上架与收款。
- **协议确认**：注册页勾选用户协议与隐私政策；论文类目展示合规范畴提示。
- **人工兜底**：首批用户由运营人工确认，异常账号可即时停用。
- **规模控制**：首批 30—50 人，单校验证后再扩到第二所高校，总人数不超过 100。

### 3.2 功能开关策略

| 开关 | 内测首批 | 内测扩量 | 公测灰度 | 说明 |
| --- | --- | --- | --- | --- |
| 注册 | 邀请码 | 邀请码 | 开放/邀请并行 | 关闭时返回明确提示 |
| 上传 | 开（人工复核） | 开 | 开 | 出问题可单独关闭上传 |
| 支付 | mock（显著标识） | 限额真实支付 | 真实支付 | 支付开关与渠道开关分离 |
| 砍价 | 关 | 开 | 开 | 先验证基础交易再开营销玩法 |
| AI 规划 | 开 | 开 | 开 | 只读推荐，风险低 |
| AI 客服 | 开 | 开 | 开 | 保留转工单兜底 |
| 收益结算 | 开（T+1） | 开 | 开 | 财务每日核对 |
| 举报/下架 | 开 | 开 | 开 | 内容风险熔断 |

开关原则：**默认关闭、白名单开启、可分钟级回退**；每个开关都要有服务端校验，不能只靠前端隐藏。

### 3.3 灰度批次

| 批次 | 范围 | 开放能力 | 进入下一批条件 |
| --- | --- | --- | --- |
| B0 内部 | 团队 5—10 人 | 全功能 + mock 支付 | 核心链路无 P0/P1，数据可回滚 |
| B1 种子用户 | 30—50 人，单校 | 上传、购买、下载、规划、工单 | 连续 3 天无 P0，支付/下载成功率 ≥ 99% |
| B2 扩量 | 80—100 人，两校 | 增加砍价、卖家结算 | 内容审核积压 < 24h，投诉闭环率 100% |
| B3 公测候选 | 邀请码 + 申请 | 接近全量 | 公测前置清单全绿 |

每批结束做一次 Go/No-Go 评审，未达标不扩量；扩量前先扩只读流量，再扩写入与交易。

### 3.4 内测期支付策略

- 首选：`PAYMENT_MODE=mock`，页面固定横幅「内测环境，支付不产生真实扣款」，避免资金纠纷。
- 如必须验证真实支付：仅接入一个渠道（建议微信），单笔限额（如 ≤ 1 元），每日总额限额，财务日结；退款流程必须同时演练。
- 无论哪种模式，结算账单都必须真实生成，验证 T+1、退款扣回与人工确认。

### 3.5 内测期数据处理

- 每日备份 + 每周恢复演练；用户删除账号请求按隐私政策在承诺时限内处理。
- 不采集身份证原件；实名材料加密存储，仅审核员可查看，查看行为写日志。
- 内测结束输出数据报告：注册—上传—成交—下载—复购—投诉，作为公测决策依据。

## 4. 公测前置检查清单

### 4.1 稳定性

- [ ] 连续 72 小时运行，无重启、无内存持续增长；5xx < 0.5%，P0/P1 为 0。
- [ ] 支付回调重复投递、乱序、超时重试均幂等；断网恢复后订单状态一致。
- [ ] 服务重启时有在途请求与结算任务，验证不丢单、不重复结算。
- [ ] 磁盘写满、数据库锁等待、上传中断三类故障各演练一次并有预案。
- [ ] 备份恢复演练成功，RTO ≤ 30 分钟，RPO ≤ 1 小时。

### 4.2 性能压测

| 场景 | 目标 |
| --- | --- |
| 资料列表/详情/搜索 | 200 并发，P95 < 300ms，错误率 < 0.5% |
| 登录/下单/支付回调 | 100 并发，P95 < 800ms，无重复扣款 |
| 上传 20MB | 成功率 ≥ 99%，P95 < 10s |
| AI 规划生成 | P95 < 1s |
| 7 天稳定性 | 无 OOM，SQLite 无持续锁超时 |

压测必须覆盖真实反向代理与 HTTPS，不只在 localhost；记录基线并留档。若写 QPS 持续超过 50 或数据库超过 2GB，先扩容/迁移再放量。

### 4.3 安全审计

- [ ] 全站 HTTPS + HSTS；HTTP 强制跳转；证书自动续期。
- [ ] 生产无演示账号、无默认密码；管理员强密码 + IP 白名单。
- [ ] 密钥、商户号、`secret.key` 不入库不入仓；定期轮换回调密钥。
- [ ] 越权矩阵测试：用户/卖家/审核/财务/超管交叉访问全部拒绝。
- [ ] 上传类型、大小、魔数、压缩包层级校验；下载鉴权；目录穿越测试。
- [ ] 限流在反向代理后仍按真实 IP 生效，伪造 XFF 无效。
- [ ] CSP、Permissions-Policy、请求体上限生效；错误响应不泄露堆栈与路径。
- [ ] 依赖审计（当前零 npm 依赖）与 Node 版本安全公告跟踪。
- [ ] 用户协议、隐私政策、论文合规提示、举报入口上线；完成 ICP 备案。
- [ ] 支付合规：平台不沉淀资金、不提供充值提现、退款原路返回。

### 4.4 异常监控

| 指标 | 告警阈值 | 处理 |
| --- | --- | --- |
| 健康检查失败 | 连续 2 次 | 立即排查进程/数据库/磁盘 |
| 5xx 比例 | 5 分钟 > 1% | 回滚或熔断对应功能 |
| 接口 P95 | 10 分钟 > 1s | 查慢查询与锁等待 |
| 支付失败率 | 10 分钟 > 5% | 检查渠道与回调 |
| 结算积压 | 到期未结算 > 20 笔 | 财务与研发联合处理 |
| 磁盘使用率 | > 80% | 清理/扩容/迁移上传 |
| 备份失败 | 任意一次 | 当日必须补做并校验 |
| 审核积压 | 待审 > 50 或最久 > 24h | 增派审核或限流上传 |

日志要求：JSON 行、含 requestId/userId/route/status/latency；不记录密码、Token、完整卡号与实名材料；按《网络安全法》要求保留 ≥ 180 天；敏感操作单独审计表。

### 4.5 回滚机制

- 发布物按版本打 tag，保留上一版可执行目录；Nginx upstream 支持一键切回。
- 发布前必备份；数据库迁移必须向前兼容（先加列后切读），禁止不可逆删列。
- 回滚触发条件：5xx 持续 > 5 分钟、支付/登录成功率 < 95%、出现资金错误、核心页面不可用。
- 回滚步骤：切流量 → 停新进程 → 恢复上一版 → 必要时恢复备份 → 健康检查 → 公告。
- 目标：代码回滚 ≤ 15 分钟；数据恢复 RTO ≤ 30 分钟、RPO ≤ 1 小时。

## 6. 用户反馈与快速修复机制

### 6.1 反馈渠道

- 站内：客服工单 + AI 客服转人工 + 资料举报。
- 站外：内测微信群/飞书群、每周一次表单问卷、关键用户 1 对 1 访谈。
- 数据：页面埋点只采集必要事件（注册、上传、支付、下载、规划、打卡），不采集敏感内容。

### 6.2 分级与响应

| 级别 | 定义 | 首次响应 | 临时处置 | 修复目标 |
| --- | --- | --- | --- | --- |
| P0 | 全站不可用、资金错误、数据泄露 | 15 分钟 | 立即回滚/熔断 | 2 小时内恢复 |
| P1 | 支付、下载、登录等核心链路受阻 | 30 分钟 | 切开关/降级 | 24 小时内 |
| P2 | 单功能异常、体验缺陷 | 4 小时 | 给出替代方案 | 下个迭代 |
| P3 | 建议、文案、样式 | 1 个工作日 | 记录 | 每周评估 |

### 6.3 热修复流程

1. 复现并记录：requestId、账号、时间、操作路径、截图。
2. 定级：P0/P1 走热修复，P2/P3 进入常规迭代。
3. 修复：最小改动，禁止顺手重构；补一条回归测试。
4. 验证：受影响套件 + 冒烟 + 手工验证核心路径。
5. 发布：备份 → 低峰发布 → 观察 30 分钟 → 记录。
6. 复盘：P0/P1 在 48 小时内输出原因、影响、改进项与责任人。

### 6.4 迭代节奏

- 每日：看板同步新增问题与 P0/P1 进展。
- 每周：一次常规发布窗口；汇总反馈、排优先级、发更新说明。
- 每两周：内测用户回访，核对「愿意继续使用」与「愿意付费」两个指标。
- 每阶段结束：Go/No-Go 评审，未达标不扩量。

## 7. 上线 Runbook（速查）

**发布前**

- [ ] 代码冻结、tag、322 项测试通过
- [ ] 生产备份完成并校验
- [ ] 环境变量核对（支付、限流、开关、`SEED_DEMO=false`）
- [ ] 预发验收通过，回滚包就绪

**发布**

- [ ] 启动新版本，`/api/health` 返回 `status=ok`
- [ ] 切换 Nginx upstream
- [ ] 冒烟：首页、登录、资料列表、规划生成、工单
- [ ] 观察 30 分钟：5xx、支付、结算、登录

**回滚**

- [ ] 切回上一版 upstream
- [ ] 停止异常进程，恢复上一版代码
- [ ] 如需恢复数据，停止服务后从备份恢复
- [ ] 健康检查通过后公告，记录事故

## 9. 明确不做的事

- 不做充值、提现与资金池；所有交易走微信/支付宝/银行卡原路。
- 不做桌面端；交付形态保持 Web 应用 + 单文件离线演示。
- 不在公测前堆叠新功能；优先稳定性、数据安全与反馈闭环。
